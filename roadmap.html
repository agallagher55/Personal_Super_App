Roadmap

A soft, living plan — priorities and rough sequencing, not a committed schedule. Revisit whenever priorities shift.

Last written 2026-09-01 · source docs: architecture_Review.md, finance/ARCHITECTURE.md, fitness/README.md

Where things stand

Tasks tracker Done
Full CRUD, categories, tags, notes — the one feature that's been end-to-end real since the start.
Fitness / Google login Done
OAuth against the Google Health API is fully implemented and confirmed live (steps, HRV, SpO2, sleep, weight). This is the Fitbit connection now — Fitbit's own Web API is being retired Sept 2026, Google Health is its replacement.
Finance dashboard Planned, not built
UI is real but reads a static seed JSON file. Plaid sync layer is fully spec'd in finance/ARCHITECTURE.md but zero code exists yet.
Real database Planned, not built
Everything today is flat JSON files. finance/schema.sql already defines the SQLite schema — standing it up is step one of the Plaid work, not a separate project.

Recommendation

Of the three things on the table — fitness/Google login, Plaid for finance, and standing up a database — the first is already shipped, and the other two turn out to be the same next step: Phase 1 of the finance plan is exactly "create data/finance.db from schema.sql." There's no separate database decision left to make.

Start Finance Phase 0–1: Plaid sandbox account, add requirements.txt (plaid-python, cryptography), stand up data/finance.db, and get the Link flow working end-to-end against Plaid Sandbox data. This is the biggest real gap in the app, it's already scoped in detail, and everything else in finance (transactions, investments, categorization) builds on it.

Soft sequencing

Up next

Finance: Link + storage

  • Plaid developer account, sandbox access (instant, free)
  • requirements.txt: plaid-python, cryptography — first third-party deps in the repo
  • data/finance.db from finance/schema.sql, plus db.py, crypto.py, plaid_client.py
  • Link flow end-to-end in Sandbox: one plaid_items row + its accounts rows
Then

Finance: transactions, and the fixes it now needs

  • /transactions/sync integration, real transaction list on /finance
  • Atomic writes + a file lock around JSON read-modify-write (cheap, closes a data-loss risk that gets worse once real bank data is involved)
  • Pull the minimal auth gate forward from Phase 5 (a public URL holding real transactions needs this sooner than "eventually")
Later

Finance: investments, categorization, going live

  • Holdings + investment transactions, net-worth/portfolio summary
  • User-editable transaction categories, spending-by-category view
  • Harden the auth gate, then flip PLAID_ENV from sandbox to production
Watch list

Not urgent, but resurface before it gets expensive

  • Flask/Django migration decision (cheap to defer now, expensive to defer once finance route code piles up on stdlib http.server)
  • Basic test suite for backend/server.py's handlers
  • Shared static/js/api.js module to stop the 4-way duplication across tasks pages
  • Nightly scheduled Plaid sync, liabilities product, holdings-history table (finance Phase 6, optional)

Full detail lives in finance/ARCHITECTURE.md (phased plan, data model, security requirements) and architecture_Review.md (the cheap-fix findings referenced above). This page is a snapshot for orientation, not a replacement for either.
